# 等待时间实测（2026-11-24）

用户确认问题发生在“文字已经出来，还要等声音”。保留已确认的声音配置 权重、参考录音、4 步采样、cfg=0、FP32 及默认语速 1.0。

## 已应用

- 补齐 Rich 15.0.0。此前日志反复出现 No module named rich，导致上游 AR 加速退回普通推理；现在真实结果 graph_enabled=true、torch_static_cuda_graph。
- 上游 TTS 与加速包混用了 PyTorch 2.9 新旧精度 API。补丁统一使用新接口、保持 IEEE FP32，并去除加速包导入时强行开启 TF32 的副作用。
- 关闭可变长度语音的 cuDNN benchmark 算法搜索。卸载音色时显式关闭加速引擎，避免工作线程保留资源。
- 播放器检查音频就绪的间隔由 1500ms 缩短到 300ms。新增任务与首次播放时间记录。

相关上游补丁收录在 patches/torch29-soundfile.patch（同时包含此前 soundfile 兼容修复）。环境快照已更新，pip check 通过。

## 有效对照

同一段中文、同一音色、语速 1.0、模型预热后，原路径两次 6.703s / 10.834s；修正后两次 5.290s / 5.179s。修正后的检查字段为 graph_enabled=true、matmul_precision=ieee、cudnn_precision=ieee。音频内容相同但时长由 17.56s 变为 18.44s；加速采样实现可改变韵律，不能声称波形逐样本相同或所有新句子音质均已由用户认可。

真实 ChatGPT MCP 调用：短句“老师，准备好了。今天想聊些什么？”本机合成 1.919s、完成到播放器上报 playing 0.065s，最终播放器 ended。该 MCP 调用整体往返 7.641s，不能把本机合成时间当作用户发送消息到开口的完整时间。另一条刚重启后的请求在本机共等待约 23.50s，说明冷启动仍显著较慢。

## 未采用

上游直接分段模式第一段 8.32s、总计 46.62s；顺序短段第一段 10.76s、总计 30.54s；编码器暂移内存未改善。均已撤回生产代码，没有发布“分段快速播放”开关。

单纯在外部设置 TF32 的试验被上游 set_seed 重置，不能据此宣称 TF32 提速。该试验未启用为日常配置。

仍需区分 ChatGPT 调用前延迟、隧道传输、本机合成、浏览器后台节流与冷启动。保持本机服务运行可保留已加载模型；本次没有配置开机自启或付费服务。后台浏览器的轮询间隔可能受系统节流，不承诺固定 300ms。
